👑 Pharaoh Agentic Engineer
=================================================

`Pharaoh <https://ubcode.useblocks.com/usage/agentic_engineer/index.html>`__ is
ubCode's *agentic engineer*. You describe your engineering process once — the
stages a requirement passes through and the evidence each stage needs — and from
then on **AI does the writing while a deterministic Rust engine does the
judging**: it computes what is done, what is missing, and what to do next, and
holds any step that has not passed an independent review.

.. epigraph::

   **AI authors. The graph judges** — AI speed, with audit-grade traceability.

This page records how the ``sphinx-needs-demo`` repository is wired for Pharaoh,
so the setup can be read and reproduced. It is a companion to the upstream
documentation, which is the authoritative reference:

* `Pharaoh Agentic Engineer — full documentation <https://ubcode.useblocks.com/usage/agentic_engineer/index.html>`__

.. caution::

   Pharaoh is an **experimental** ubCode feature. The ``ubc agent`` command is
   hidden from ``ubc --help`` and its JSON shapes may still change; pin your
   ``ubc`` version and expect breaking changes between releases. The quality
   gate additionally needs a ``ubc`` built with quality analysis (ubCode
   PR #2246).

The mental model
----------------

If you have used ``make``, you already have it: ``ubc agent next`` is *make for
your requirements*. It looks at what exists and names the **single next thing to
build**. You — or your AI assistant — build exactly that one step; the engine
re-checks the graph and names the next. Repeat until nothing is left.

.. code-block:: text

   ubc agent next  ─▶  author one stage  ─▶  ubc agent gaps / status
        ▲                (skill or by hand)          │
        └────────────── repeat until "done" ◀────────┘

Six words cover the whole system: a **stage** is one declared step of the
process; a **gate** is a per-stage rule that must pass (trace links present, code
covered, review done); a **gap** is one unmet obligation attributed to a stage; a
**stream** is one feature's slice of the graph; the **heartbeat** is the single
deterministic evaluation that resolves every stage to ``done`` / ``ready`` /
``blocked``; and a **verdict** is an independent review record. See the
`overview <https://ubcode.useblocks.com/usage/agentic_engineer/index.html>`__ for
the glossary in full.

How this demo is wired
----------------------

The demo was bootstrapped with ``ubc agent install`` from the default **vmodel**
profile (the V-model), and everything Pharaoh reads lives in files that are
committed to the repository. There is no hidden state: the process model and the
review rubric sit in the same ``docs/ubproject.toml`` the project already uses for
its need types and linting.

.. note::

   This project's ``ubproject.toml`` is under ``docs/``, so every command below
   pins that directory with ``-p docs`` (a repository can hold several
   ``ubproject.toml`` files). Run them from the repository root.

.. list-table::
   :header-rows: 1
   :widths: 34 46 20

   * - File / directory
     - Purpose
     - Tracked in git?
   * - ``docs/ubproject.toml``
     - The ``[workflow]`` process model (stages, routes, trace gates) and the
       ``[quality]`` review gate, alongside the existing need types and links.
     - yes
   * - ``docs/quality/*.toml``
     - Per-type **criteria packs** — the scored rubrics reviews are graded
       against (``feat``, ``requirement``, ``arch``, ``decision``).
     - yes
   * - ``docs/.pharaoh/agent/install-manifest``
     - Records every profile-owned file and its baseline (profile ``vmodel``,
       version 5), so ``ubc agent update`` can tell your edits from the profile's.
     - yes
   * - ``docs/.pharaoh/verdicts/<ID>.json``
     - One AI-review **verdict** per reviewed need — the durable, shared record
       of what passed review.
     - yes
   * - ``.claude/skills/<name>/SKILL.md``, ``.claude/commands/ubc-agent-next.md``
     - The authoring/review **skills** and the loop driver, for Claude Code.
     - yes
   * - ``.github/agents/<name>.agent.md``
     - The same skills exposed as GitHub Copilot agents (plus ``workflow-author``).
     - yes
   * - ``docs/_build/…/needs.json``
     - The built graph the engine reads. Generated by ``sphinx-build``.
     - no (build output)

.. tip::

   Commit ``docs/.pharaoh/``. It is not rebuildable state — it holds the install
   manifest and your team's review verdicts. A leading-dot directory is easy to
   overlook, but gitignoring it loses the review history and makes
   ``ubc agent update`` / ``ubc agent doctor`` report the install as missing.

The V-model pipeline
--------------------

The ``[workflow]`` section declares the demo's stages in order. Elicitation
(``need``) is deliberately the **first** stage, so on a greenfield feature
``ubc agent next`` starts there rather than at the reference roots (``team`` /
``release``):

.. code-block:: text

   need → req → arch → swreq → swarch → impl → test

plus the ``team`` / ``person`` / ``release`` reference data those stages trace
against. Each stage produces one need type, declares which stages it
``depends_on``, and declares the trace links it must satisfy — in this project
mostly the generic ``links`` option, with a few typed edges (``author``,
``release``, ``implements``, ``mitigates``, …). Here is the ``req`` stage, which
authors requirements under ``docs/automotive-adas/`` and holds itself for review:

.. code-block:: toml

   [[workflow.stages]]
   id = "req"
   produces = "req"
   depends_on = ["need", "person", "release"]
   author_skill = "draft-requirement"
   review_skill = "review-requirement"

   [workflow.stages.route]
   scope = "feature"
   granularity = "per-root"
   path = "automotive-adas/sys_2_req_analysis.rst"

   [[workflow.stages.trace]]
   up = "need"
   link = "links"
   direction = "both"

The lower two arms of the V are special: ``impl`` and ``test`` are materialised
from one-line **codelinks** markers in the real source rather than authored as
``.rst`` directives, so implementation and test coverage are graph facts derived
from code.

The remaining stages — ``spec``, the parallel safety V
(``hazard → safety_goal → fsr → sysreq → sys-arch``), and the detailed
``layer`` / ``interface`` / ``component`` / ``seq_msg`` design — are **declared
but not yet skilled**: they are outside the ``automotive-adas`` scope this setup
targets. Full key-by-key reference:
`Configuring the workflow <https://ubcode.useblocks.com/usage/agentic_engineer/configuration.html>`__.

Reviews and quality
-------------------

A stage that names a ``review_skill`` gains a **substance gate**: it is held
``ready`` — never reported ``done`` — until every need it produced carries a
fresh review verdict that clears the floors in ``[quality]``. The split is the
point — the AI never grades its own homework:

* **The AI measures.** For each reviewed need an LLM scores every axis of the
  matching criteria pack — a number, a reason, and a suggestion.
* **The engine judges.** Pass/fail is computed from the per-axis floors in
  ``[quality.required]``, deterministically and at read time.
* **The IDE explains.** Scores and freshness surface as lenses and a panel in
  VS Code.

This demo enables the gate with a single global floor — ``parent_fit = 1`` — which
every reviewed type's pack carries. The rubric lives as data in
``docs/quality/*.toml``, so the ``review-*`` skills stay generic. The requirement
pack, for example:

Verdicts are written to ``docs/.pharaoh/verdicts/<ID>.json`` by
``ubc agent verdict-submit`` (which stamps the provenance and content
fingerprints — you never hand-write one). A verdict **expires** when the need it
judged, its one-hop neighbourhood, or the rubric changes, so an edited need
re-reddens its stage until it is re-reviewed. See
`Reviews and quality analysis <https://ubcode.useblocks.com/usage/agentic_engineer/quality.html>`__.

Driving the loop on this demo
-----------------------------

Ask the engine what to do next, anchored on a stream (any need id works —
``REQ_001`` and its subtree, say):

.. code-block:: bash

   ubc agent next -p docs --id REQ_001

It returns **at most one** stage as JSON — the ``produces`` type, the ``route``
to write to, the recommended ``skill``, and the gate still to close. There are
three ways to author it:

**With your AI assistant (recommended).**
   In Claude Code, invoke the ``drive-workflow`` skill or the ``/ubc-agent-next``
   command; in Copilot, the ``workflow-author`` agent. It runs ``ubc agent next``,
   authors the artefact at the reported route with the required trace links, and
   leaves the result **uncommitted** for you to review. ``drive-workflow`` advances
   exactly one stage and then stops — you decide when to drive the next.

**Headless.**
   ``ubc agent run -p docs --id REQ_001`` assembles the prompt and executes it
   through the configured runner, then rebuilds and reports what was produced.

**By hand.**
   Nothing stops you writing the ``.rst`` directive (or the code marker)
   yourself; the engine only cares about the resulting graph.

After each step, confirm the gap closed and watch the heartbeat:

.. code-block:: bash

   ubc agent gaps -p docs --scope REQ_001   # structural gaps for one stream (non-zero if any)
   ubc agent status -p docs                 # one row per stage: done / ready / blocked

A feature is finished only once the combined gate is green — both the structural
gaps and the review verdicts clear:

.. code-block:: bash

   ubc agent release-check -p docs --with-verdicts

Beyond the core loop, the installed skills also cover **decisions**
(``record-decision`` → ``decision`` needs, gated by ``quality/decision.toml``)
and **change impact** (``change-request``, which reconciles each downstream stage
after an upstream need is edited).

Onboarding an existing project
------------------------------

This repository already had a Sphinx-Needs graph before Pharaoh. Brownfield mode
**derives** a drivable ``[workflow]`` from the links your needs actually use,
instead of the blank profile defaults:

.. code-block:: bash

   ubc agent install -p docs --detect --plan   # preview the derived workflow as JSON
   ubc agent install -p docs --detect          # write it (never clobbers existing config)

Structural edges become trace gates; anything the engine cannot infer is raised
as an open question carrying its evidence. The **pharaoh-onboard** skill runs this
end to end — it executes the plan, answers each question from the structural
signal, and iterates to a clean, drivable workflow.
